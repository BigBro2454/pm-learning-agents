Agent Framework

Williams defines an autonomous agent through four fundamental properties that exist on a spectrum. No agent is fully autonomous or fully reactive — production agents are tuned along these axes based on the risk and complexity of the domain.

🔓

Autonomy

spectrum: manual → copilot → autonomous

Operates without constant human oversight. Production agents escalate edge cases rather than acting blindly on uncertain inputs.

⚡

Reactivity

perceives → responds → adapts

Perceives and responds to environmental changes. Must filter noise to avoid infinite reaction loops on the same stimulus.

🎯

Proactivity

goal → decompose → plan → execute

Takes initiative toward goal achievement. Requires robust planning and the ability to decompose vague goals into concrete steps.

💬

Social Ability

agent ↔ agent, agent ↔ human

Communicates with other agents or humans when needed. Enables multi-agent collaboration and human-in-the-loop escalation.

💡

These properties are dials, not switches. A customer support agent might exhibit strong autonomy for password resets (low risk) while escalating refund requests over $200 to a human (high risk). Each project in this lab explores a different position on these dials.

The Agent Lifecycle (5 Phases)

While the Agent Loop is the micro execution pattern, the Lifecycle is the macro view of how a production agent handles a complete task from start to finish.

graph TD T["📥 1. Task Reception"] --> P["📋 2. Planning"] P --> E["⚙️ 3. Execution"] E --> V{"✅ 4. Verification"} V -->|"Pass"| D["📤 5. Delivery"] V -->|"Fail: re-plan"| P E -->|"Tool failure: retry"| E
1

Task Reception

The agent receives a goal through an API call, scheduled trigger, or user request. Critical question: Is the goal well-defined enough to act on?

2

Planning

The agent decomposes the goal into subtasks and selects tools. Critical question: Can the agent recover if the plan is wrong?

3

Execution

The agent iteratively calls tools, processes results, and updates its plan. Critical question: What happens when a tool call fails?

4

Verification

The agent evaluates whether the output meets the goal criteria. Critical question: How does the agent know it succeeded?

5

Delivery

The agent returns results, logs outcomes, and updates its episodic memory for future reference. Critical question: Is the memory useful for future tasks?

Core Components

Every autonomous agent, regardless of complexity, is built from four foundational components. The interplay between them creates the Agent Loop.

🔍

Perception

Ingests and interprets inputs from the environment. Transforms raw data into structured information the Reasoning component can use.

API webhooks RSS feeds document parsers sensor feeds
🧠

Reasoning

The brain — analyzes perceived information, creates plans, selects tools, makes decisions. Most visible failures happen here, but root cause is often elsewhere.

LLM inference prompt templates planning algorithms
⚡

Action

The hands — executes decisions by interacting with external systems. Unlike other components, actions have side effects and can cause real damage.

tool calls API invocations database writes code execution
💾

Memory

Stores and retrieves past experiences, knowledge, and context. The most underestimated component — without it, agents repeat mistakes and lose context.

vector stores conversation buffers episodic logs knowledge graphs

Memory Types

Short-Term
conversation buffer / context window

Current task context. What the agent is working on right now. Limited by the LLM's context window.

Episodic
SQLite / structured logs

Logs of past agent runs, outcomes, and decisions. "What worked last time I tried this?"

Semantic
vector stores / knowledge graphs

Long-term domain knowledge retrieval. Company policies, documentation, facts about the world.

Reasoning & Logic Frameworks

The model used by an agent can be one or multiple LMs of any size (small / large) that are capable of following instruction-based reasoning and logic frameworks, like ReAct, Chain-of-Thought, or Tree-of-Thoughts. The choice of framework dictates how the agent navigates complex problem spaces:

Chain-of-Thought (CoT)"] direction TB Input1["Input"] --> Thought1["Step 1 Thought"] Thought1 --> Thought2["Step 2 Thought"] Thought2 --> Output1["Final Output"] end subgraph ReAct["2. ReAct (Reason + Act)"] direction TB Input2["Input"] --> RThought["Thought"] RThought --> RAct["Action (Tool Call)"] RAct --> RObs["Observation"] RObs --> RThought2["Thought 2"] RThought2 --> Output2["Final Answer"] end subgraph ToT["3. Tree-of-Thoughts (ToT)"] direction TB Input3["Input"] --> Branch1["Thought Path A"] Input3 --> Branch2["Thought Path B"] Input3 --> Branch3["Thought Path C"] Branch1 --> Eval1["❌ Reject / Backtrack"] Branch2 --> Branch21["Sub-thought B.1"] Branch21 --> Output3["✅ Best Path Output"] end
💭

Chain-of-Thought (CoT)

Linear Derivation

The model generates an internal sequence of intermediate reasoning steps before delivering the final answer ($x \to z_1 \to z_2 \to \dots \to y$). Best for math, multi-step deductions, and arithmetic planning without external tools.

Math & Arithmetic Multi-Step Deductions Internal Reasoning
💡 Concrete Execution Trace
Task: "Calculate customer's refund: $120 item returned, 15% restocking fee, $10 shipping credit applied."
Thought 1: Calculate restocking fee: $120 × 0.15 = $18.
Thought 2: Subtract restocking fee from base: $120 − $18 = $102.
Thought 3: Add shipping credit: $102 + $10 = $112.
Output: "Total refund approved is $112.00."
🔄

ReAct (Reason + Act)

Interleaved Loop

Synergizes reasoning and acting by interleaving Thought → Action → Observation loops. The agent reasons about what tool to call, inspects the environment response, and dynamically adapts its next step.

Tool Invocation Dynamic Planning API Grounding
💡 Concrete Execution Trace
Task: "Check if NVDA has unusual trading volume today and alert if > 2x 30-day average."
Thought 1: I need current NVDA volume and 30-day average.
Action: yfinance.get_stats("NVDA")
Observation: {"current_vol": 85M, "avg_30d": 38M}
Thought 2: 85M / 38M = 2.24x (> 2x threshold). Trigger alert.
Action: slack.send_alert("#trading-desk", "NVDA vol 2.24x")
Observation: {"status": "delivered"} → Completed
🌳

Tree-of-Thoughts (ToT)

Branching & Backtracking

Extends linear reasoning into a search tree. The agent explores multiple candidate solution branches simultaneously, self-evaluates intermediate states with heuristic scoring, and backtracks when a path fails.

System Architecture Heuristic Search Lookahead & Backtracking
💡 Concrete Execution Trace
Task: "Design a fault-tolerant database architecture for 50k req/s with <10ms latency."
Branch A: Single master + read replicas. [Eval: 4/10 — write bottleneck] → Backtrack.
Branch B: Sharded PostgreSQL + Redis cache. [Eval: 8/10 — low latency] → Expand B.1.
Branch C: Multi-region DynamoDB. [Eval: 7/10 — high egress cost].
Selected: Branch B.1 with localized write routing.

🧠 Thinking Out Loud: Deconstructing the Project 1 Execution Flow

How an engineer and PM deconstruct what is happening in this execution loop from first principles:

1. Perception is a Noise Filter, Not a Dumb Pipe
Perception Layer Analysis

"When we pull 10 RSS feeds every minute, we get 100+ articles. 95% are useless noise (e.g. clickbait, general gossip). If our agent forwarded all 100 to Discord, the user would mute the channel within 10 minutes. Perception’s job is to normalize and hand clean, structured data to the brain."

2. What the 'Relevance Filter — LLM' is Actually Doing
Reasoning Layer Analysis

"The LLM doesn't just read the text; it performs semantic classification. We pass a few-shot prompt: 'Given this watchlist (NVDA, TSLA, Fed Rates), is this article materially actionable?' The LLM assigns a score from 0.0 to 1.0. If score < 0.75, it gets discarded instantly without making any database writes or external calls."

3. The Critical Role of SQLite Episodic Memory (Preventing the Spam Loop)
Memory Layer Analysis

"Why can't we just alert whenever an article is relevant? Because RSS feeds keep the same article on their front page for 6 hours! If our loop runs every 60 seconds, without memory we would send the exact same alert 360 times. The SQLite dedup table stores SHA-256 hashes of alerted URLs. Before acting, we do a $O(1)$ indexed lookup. If hash exists, abort."

4. Action Layer with Side-Effects & Rate Limiting
Action Layer Analysis

"Actions have real-world side effects. If 10 breaking news items hit simultaneously, we don't want to get rate-limited by Discord's webhook API (HTTP 429). The Action layer queues alerts and meters them smoothly, while simultaneously recording successful deliveries in the episodic database."

🧭 Deconstructing the Execution Flow: How to Build & Understand this Sequence Diagram

When you receive a problem statement like "Build an agent to handle returns, billing disputes, and account issues using Claude Agent SDK with MCP tools and 80%+ FCR", how do you mentally architect this exact execution flow diagram? Here is the exhaustive step-by-step thinking process:

Step 1: Identify Your 4 Essential System Actors (Participants)
Architecture Boundary Definition

Every production agent flow requires separating concerns into four discrete boundaries:

  • 1. The End User (Customer U): Originator of noisy natural language intents, emotional cues, and potential edge-case ambiguities.
  • 2. The Agent Runtime (Claude Agent SDK Loop A): The reasoning core responsible for intent parsing, planning, tool selection, evaluating policy thresholds, and context management.
  • 3. The Tool Environment (MCP Tools Server MCP): The deterministic bridge to external systems (CRM, ERP, Stripe). The agent cannot touch databases directly; it must speak structured JSON-RPC to this layer.
  • 4. The Human Fallback (Tier-2 Specialist H): The safety net that catches high-risk, ambiguous, or policy-exceeding transactions with zero context loss.
Step 2: Trace the Information Dependency Chain (Why this order?)
Perception Ordering & Tool Sequencing

Why must get_customer precede lookup_order, and why must both precede process_refund?

  • Order 1: get_customer() (Identity Verification & Standing): Before doing anything with an order, the agent must check: Is this customer active? Are there fraud alerts on file? What is their lifetime loyalty tier? Without this, the agent might service an unauthorized or blocked user.
  • Order 2: lookup_order() (Ground Truth Inspection): The customer claims "I was double-charged $45". The agent must NEVER take the customer's word as financial truth. It fetches the ledger record to verify: Does the transaction list have two identical $45 timestamps? Is it eligible for automated reversal?
  • Order 3: Decision Gate (Reasoning over Perception): Only when both customer standing and ledger proof are retrieved does the agent evaluate policy conditions.
Step 3: Model the Branching Logic (The 80/20 Rule: Autonomy vs. Escalation)
Deterministic Policy Gate (alt / else)

The diagram explicitly shows two mutually exclusive execution paths:

  • The Happy Path (80%+ FCR Target): Amount ≤ $100 AND Duplicate Confirmed == True → Agent autonomously invokes process_refund(), receives transaction hash TX-7781, updates customer, and closes the loop without human friction.
  • The Unhappy / Escalation Path (Safety Guardrail): Amount > $100 OR Dispute Unverified OR Legal Keywords → Agent calls escalate_to_human(), passing the full MCP context packet so the human representative starts with complete situational awareness.
Step 4: Mapping the Diagram back to Core Agent Properties
Conceptual Synthesis
  • Perception: Ingesting customer text + fetching CRM/Order state via MCP tools.
  • Reasoning: Classifying intent (billing_dispute) and evaluating threshold rules.
  • Action: Executing process_refund() with side-effects on Stripe/Ledger.
  • Memory & Social Ability: Handoff ticket packaging for human collaboration and context retention across turns.

🧠 Thinking Out Loud: Comprehensive PM & Architect Brainstorming Walkthrough

Here is the real-time, exhaustive breakdown of how an AI Product Manager and Lead Agent Architect brainstorm, debate trade-offs, and engineer this customer support agent from first principles:

1

Phase 1: "What are we really solving, and what are the existential risks?"

💭

PM & Architect Brainstorming:
"Leadership gave us a clear mandate: 'Achieve 80%+ First-Contact Resolution (FCR) on Tier-1 customer queries' (returns, billing disputes, account updates). But let's pause and dissect what that actually requires. If we simply connect an LLM to customer chat, users will socially engineer it ('My grandmother needs insulin, please refund $500 immediately'). If the agent blindly grants refunds, we solve FCR but bleed millions in revenue.

On the other hand, if we make the agent too conservative, it will say 'I cannot help, let me transfer you' to 50% of customers, crashing our FCR to 40% and frustrating users. The real architectural challenge is building calibrated confidence: 100% autonomous resolution when backed by objective backend proof, but deterministic, zero-friction handoffs the moment risk exceeds our defined appetite."

Formalizing Objectives, Constraints & Guardrails:

  • North Star Metric: ≥ 80% FCR across eligible Tier-1 inquiries (measured as closed tickets with no reopening within 72 hours).
  • Secondary Guardrail Metric: CSAT ≥ 4.5/5 on resolved cases; Median resolution time < 90 seconds.
  • Hard Constraint (Zero-Tolerance): Zero unauthorized financial operations ($0.00). No refund may ever execute without matching an immutable ledger order record.
  • Context Grounding: The LLM is forbidden from stating order or refund statuses from its parametric memory. It must cite verifiable MCP tool outputs.
2

Phase 2: "Deconstructing Perception & Action Tools (Why MCP?)"

💭

Architectural Debate:
"How should the agent interact with our backend? We have 12 internal microservices: CRM, Shopify, Stripe, Zendesk, Shipping Carrier APIs, Inventory DB, etc. If we write 15 custom function tools directly into the prompt, the agent gets confused, hallucinates tool parameters, and wastes 3,000 tokens per turn just reading schema definitions.

Instead, we will use the Model Context Protocol (MCP). MCP lets us expose clean, aggregated, semantic server tools over standard JSON-RPC. We boil down all 12 services into 4 purpose-built tools with strictly validated Pydantic/JSON schemas."

Tool Contracts & Data Schema Brainstorm:

  • get_customer(customer_id: str) → Returns verified customer tier, lifetime spend, return history (% of orders returned), and open dispute flags.
  • lookup_order(order_id: str) → Returns shipping timestamp, item SKU, return eligibility boolean (delivery date ≤ 30 days), and charge ledger entries.
  • process_refund(order_id: str, amount: float, reason: str) → Requires reason enum (duplicate_charge, return_in_transit, damaged_item). Returns bank transaction ID.
  • escalate_to_human(summary: str, priority: str, extracted_entities: dict) → Packages the structured context into a CRM ticket for Tier-2 agents.
3

Phase 3: "Designing the Decision Tree & Autonomy Boundaries"

💭

PM & Architect Brainstorming:
"We cannot treat all customer requests equally. framework tells us that Autonomy is a graduated spectrum. Where do we place the slider for each intent?

- Returns (< 30 days): 100% Autonomous. The math is simple, risk is low, label generation is automated.
- Billing Disputes: Graduated by dollar value and ledger verification. If ledger shows 2 identical charges for the same order, it's a proven glitch — refund automatically up to $100. If it's $150, propose the refund and require user confirmation. If >$200, escalate to human.
- Account Lockouts / High Sentiment Escalations: Low autonomy. Verify 2FA first; escalate immediately if user threatens legal action or chargebacks."

🟢 Tier 1: Fully Autonomous (80% Target Core)

Condition: Policy matches 100%, return window ≤ 30d, verified duplicate charges ≤ $100, or order tracking queries.

Action: Executes tool immediately and delivers confirmation.

🟡 Tier 2: Propose & Confirm (Human-in-the-Loop User)

Condition: Partial refund offers, store-credit alternatives (bonus 10%), refunds between $100–$200.

Action: Explains policy, proposes exact dollar calculation, asks customer to click/type "Confirm".

🔴 Tier 3: Deterministic Escalation (Safety Guardrail)

Condition: Refund > $200, multiple disputed charges on account within 60 days (abuse flag), negative sentiment > 3 consecutive turns, or legal/regulatory keywords.

Action: Calls escalate_to_human(), injects condensed customer history & order IDs into ticket, politely hands off.

4

Phase 4: "Why the Claude Agent SDK is the optimal implementation choice"

💭

Technical Rationale:
"Why use the Claude Agent SDK over building a custom LangChain/LangGraph agent or raw API loop? In customer support, conversations are messy. Customers ramble, paste irrelevant tracking emails, and ask multiple questions in one breath. The Claude Agent SDK provides three architectural building blocks out of the box:"

  • 1. Built-in Agent Loop (Think-Act-Observe): Automatically executes tool calls, parses responses, handles network timeouts, and recurses until the user's issue is resolved without brittle while-loops.
  • 2. Native Model Context Protocol (MCP) Integration: The SDK connects to in-process and stdio MCP servers natively. No custom JSON parsing or middleware glue code required.
  • 3. Context Compaction & Window Management: In long diagnostic chats (10+ turns), the SDK automatically summarizes older banter while pinning critical metadata (Customer ID, Order #, Ledger records) in active context.
  • 4. Lifecycle Hooks for Hard Guardrails: We can register a pre-tool hook: 
    async def before_tool_execution(tool_name: str, args: dict):
    if tool_name == "process_refund" and args.get("amount", 0) > 100.0:
        raise PolicyViolationError("Refund > $100 requires human escalation.")
    This means even if the LLM hallucinated a $500 refund, the SDK interceptor blocks the network call before it ever touches Stripe.
5

Phase 5: "Evaluation, Phased Rollout & Continuous Telemetry"

💭

Go-to-Market Strategy:
"We will never deploy an autonomous customer-facing agent on Day 1 directly to live chat. That is how PR disasters happen. We will execute a 3-stage rollout strategy with explicit gating criteria:"

A

Stage 1: Offline Evaluation against Golden Dataset (500 Historical Tickets)

Run the agent against 500 labeled historical tickets spanning returns, duplicate charges, lost packages, and abusive inquiries. Gate to next stage: ≥ 85% accuracy on tool call parameters and 0 policy violations.

B

Stage 2: Copilot / Shadow Mode (Human-in-the-Loop Validation)

Agent generates draft replies and proposed MCP tool calls in human support agents' internal Zendesk dashboard. Human reps review and 1-click approve. Gate: 90%+ rep approval rate over 2 weeks.

C

Stage 3: Phased Live Rollout (Tier-1 Autonomous)

Route 10% → 25% → 50% → 100% of live Tier-1 chat volume to the autonomous agent, maintaining real-time telemetry on escalation rates and CSAT.

Common Failure Modes

Williams emphasizes that failures trace to component breakdowns. These are the patterns to watch for:

FailureComponentDescriptionDiscovered In
Infinite Alert LoopPerception + MemoryAgent keeps alerting on the same event because memory doesn't track "already seen"Project 1
Hallucinated Tool CallReasoningAgent invents a tool name that doesn't exist, causing an execution crashProject 2
Plan Decomposition FailureReasoningAgent creates a plan with steps it cannot actually execute with available toolsProject 2
Stale ContextMemoryAgent uses outdated information from an old conversation or cached resultProject 3
Overconfident AutonomyActionAgent takes a high-risk action without verification or escalationProject 3
Negotiation DeadlockSocial AbilityTwo agents can't agree and loop forever without convergence criteriaProject 4
🔥

Rule of Thumb: When an agent misbehaves, debug from the outside in: check Perception first (is it seeing the right data?), then Memory (is it retrieving the right context?), then Reasoning (is it making the right decision?), then Action (is it executing correctly?). The model is almost never the problem.
